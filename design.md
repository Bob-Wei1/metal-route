## Problem Statement

There is no open-source, GPU-accelerated PCB autorouter, and nothing in the PCB
routing world runs on Apple Silicon's Metal. The mature GPU routing research
(GAMER, CUGR, FastGR) is all CUDA and all aimed at VLSI/chip scale. The open PCB
routers are CPU-only: Freerouting (Java, push-and-shove) and tscircuit-autorouter
(TypeScript, hypergraph capacity-mesh). The builder wants to learn the *whole
stack* — PCB place-and-route theory AND GPU compute — by building a vertical
slice himself: his own routing algorithm and his own Metal kernel, in a new repo,
reusing only KiCad file parsing ("kicad cruncher").

This is explicitly a learning + craft + open-source-contribution project, not a
startup and not solving an urgent blocker (bed-of-nails already routes via
Freerouting through its DSN/SES bridge).

## What Makes This Cool

- **It's genuinely empty territory.** First GPU maze router on Apple Silicon
  Metal; first GAMER-style parallel-sweep routing benchmarked on an *open PCB*
  dataset. Crossing GAMER (CUDA, chip-scale) with the PCB world on Metal is novel.
- **It teaches two hard things at once** that rarely sit in the same project:
  routing (grid models, cost fields, congestion, net ordering, rip-up) and GPU
  data-parallel algorithm design (the prefix-min scan reformulation, threadgroup
  memory, avoiding atomics and divergence).
- **The "whoa" is honest and reproducible:** "CPU and Metal agree on the routed
  output, and Metal routes N independent nets/second faster on my M-series" —
  with numbers anyone can re-run on the public dataset.

## Constraints

- **Platform:** macOS / Apple Silicon, native Metal compute (Rust + `metal-rs`,
  or Swift + Metal Shading Language). Metal-first is a deliberate choice for
  learning the hardware; the accepted cost is the router won't run on
  Linux/Windows, which caps adoption (see Premises).
- **New repo.** Clean slate. Reuse "kicad cruncher" for KiCad file parsing AND the
  existing bed-of-nails DSN/SES bridge for the Freerouting handoff. Everything else
  is built by hand.
- **Build by hand:** routing IR/model, grid, cost field, the maze/sweep algorithm,
  and the GPU kernels. These are the learning surface — do not outsource them.
- **Reuse / defer:** detailed routing (DRC-legal tracks, push-and-shove) is handed
  to Freerouting via Specctra DSN/SES (the builder already has working DSN/SES code
  in bed-of-nails), or deferred entirely in early milestones.
- **Solo, paced over weekends.** No deadline. Each stage must be independently
  runnable and demoable so momentum never depends on the whole thing working.

## Cross-Model Perspective

An independent Claude subagent (cold read, had not seen the conversation) returned:

- **Steelman:** Port the GAMER sweep-scan idea out of CUDA/VLSI into the PCB world
  on Metal, validate as a reproducible benchmark on the tscircuit dataset, then hand
  the global solution to Freerouting via the DSN/SES bridge. The artifact is "first
  GPU maze router on Apple Silicon Metal + first GAMER-style benchmark on an open PCB
  dataset + writeup." Clean, defensible, finishable.

- **Most dangerous assumption:** That the GPU is the interesting part of the
  *learning*. PCB grids are tiny vs VLSI; GAMER's 16-20x comes from million-cell chip
  grids where launch/transfer overhead amortizes. On a single PCB net a competent CPU
  A* can BEAT a Metal kernel once host↔GPU dispatch latency is counted. Proof: profile
  a CPU Lee/A* baseline FIRST; if it routes the largest dataset board in <~50ms, the
  GPU is a vanity exercise on *single-net* latency.
  - **Design response:** The GPU value proposition for this domain is **batch
    parallelism across many independent nets** (bed-of-nails-style boards have
    hundreds of point-to-point nets), not single-net wavefront speed. The benchmark
    measures nets/second on batch workloads, and the CPU baseline is built first
    precisely to expose where GPU does and doesn't help.

- **The 50% you get free:** GAMER paper + CUGR source (algorithm); tscircuit-
  autorouter (dataset + format reference; note the oracle is CPU self-consistency, not
  the dataset itself — see "A note on correctness oracle"). **The 50% you build:** the Metal port
  (CUDA scan/`simd_shuffle` semantics don't translate for free), the PCB model
  (layers, vias, pad clearance, net ordering, rip-up — GAMER's coarse stage handles
  none of this), and the DSN/SES bridge. The PCB model is where most of the routing
  learning lives.

- **GPU warning (critical):** The naive per-cell wavefront with atomic relaxation is
  exactly the version that performs terribly (atomic contention + branch divergence)
  and teaches the wrong lesson. GAMER's whole trick is that it does NOT do per-cell
  atomics — it reformulates expansion as a **separable prefix-min scan along rows then
  columns**. The parallelism is in the scan, not the frontier. Build the naive BFS and
  you will wrongly conclude "GPU routing is pointless." The design commits to the
  row/column min-scan — **but only after a milestone-0 spike confirms the separable
  H-then-V min-sweep actually reproduces Lee's BFS shortest-path result on
  obstacle/clearance grids.** This is the single largest unproven assumption in the
  design: GAMER's separability is established for its own cost formulation, and the
  PCB obstacle/via model may not decompose cleanly. De-risk it before M4 (see M0).

- **Meta-note:** As originally scoped the slice was ~80% GPU kernel, which fights the
  "whole stack" goal. **Re-sequencing (CPU baseline first) rebalances it** to ~40%
  routing model + 40% GPU + 20% bridge — the whole-stack balance actually wanted.

## Approaches Considered

### Approach A: "Earn the GPU" — CPU-first vertical slice, then Metal upgrade (CHOSEN)
Build a single/multi-layer grid maze router on CPU end-to-end first (parse → grid
model → Lee/A* → route → emit), correct and benchmarked on the tscircuit dataset.
THEN port the wavefront to Metal as a GAMER-style row/column prefix-min sweep, proving
speedup on batch-of-nets. Detailed routing deferred to Freerouting via DSN/SES.
- Effort: L (human ~6-10 weekends / CC: paced over weeks). Risk: Low for M1-M3.
  **M4 is High inherent risk, reduced to Medium by the M0 gate** — the prefix-min sweep
  reformulation is the tricky, easy-to-get-wrong part this document warns about at
  length; the M0 CPU spike + M2 go/no-go gate are what bring residual risk down.
- Pros: CPU baseline IS the routing lesson and the GPU correctness oracle; every stage
  is runnable/demoable; honest benchmark numbers; matches whole-stack balance.
- Cons: GPU gratification is delayed; two wavefront implementations (CPU + GPU) to keep
  in sync.
- Reuses: kicad cruncher (parse), bed-of-nails DSN/SES code (Freerouting handoff),
  tscircuit autorouting dataset (benchmark + oracle).

### Approach B: "Metal-first" — GPU kernel as the spine from day one
Start with the Metal prefix-min sweep kernel; build the router around it. CPU only as
a tiny reference.
- Effort: L/XL. Risk: High.
- Pros: Maximum immediate GPU learning; forces internalizing the scan reformulation.
- Cons: High risk of the "GPU is pointless" trap if benchmarked wrong; routing model
  under-learned (fights whole-stack goal); no correctness oracle until late; GPU-only
  debugging is brutal.

### Approach C: "Batch-of-nails benchmark engine" — lateral framing
Specialize the whole project to bed-of-nails-style boards (hundreds of independent
point-to-point test-point→connector nets). GPU value prop = "route N independent nets
concurrently," published as nets/second + a niche open tool for the fixture/test
community.
- Effort: L. Risk: Med.
- Pros: Plays to the one workload where GPU parallelism is obviously real; narrow,
  finishable, genuinely novel; feeds bed-of-nails directly.
- Cons: Narrower routing lesson (point-to-point, less general congestion); smaller
  audience.

## Recommended Approach

**Approach A**, with **Approach C folded in as the headline benchmark workload.**

A is the only approach whose *sequence* matches the goal: the CPU baseline teaches
routing and produces the oracle the GPU must match; the Metal port then teaches GPU on
solid, verifiable ground; and the builder is never stuck holding an unrunnable pile of
kernel code. C's framing ("route many nets concurrently") is the workload where Metal is most
likely to show an honest speedup. But keep the roles straight: **general multi-net
dataset boards stay the primary correctness target** (that's where the whole-stack
routing learning lives), and **bed-of-nails-style batch boards are a secondary
throughput showcase**, not the headline — otherwise the benchmark drifts toward the
easy embarrassingly-parallel case and the real routing lesson gets under-exercised.
B is the trap the cold read explicitly warned against.

## Open Questions

1. **Language for the host side:** Rust + `metal-rs` (closer to systems learning,
   easy CLI + benchmark harness, plays well with a future WebGPU/`wgpu` port) vs Swift
   + MSL (most idiomatic Metal, best Apple tooling/Instruments GPU debugging). Leaning
   Rust for portability optionality and CLI ergonomics; decide before milestone 2.
2. **What exactly is "kicad cruncher"?** Confirm it parses `.kicad_pcb` into something
   with pad positions, net names, layer stackup, and board outline — the minimum the
   grid model needs. If it doesn't expose nets+pads cleanly, that's the first integration spike.
3. **Grid resolution / model:** uniform fine grid vs coarse global-routing grid (GCells)
   first. GAMER operates on a coarsened grid; starting coarse keeps grids small and the
   scan tractable.
4. **Routing direction model:** pure rectilinear (H/V + vias) to match the sweep
   decomposition cleanly, or allow 45°? Rectilinear first — it's what the GAMER sweep
   assumes.
5. **Does the tscircuit dataset format map cleanly to a grid + nets, or is a small
   adapter needed?** Likely an adapter; scope it in milestone 1.

### A note on "correctness oracle"

The tscircuit dataset provides input geometry, not known-good routed solutions, so it
is NOT a ground-truth oracle. Correctness is established three ways: (a) the M1 32x32
case checks routed path length against a hand-computed value; (b) from M3 on, the
**CPU result is the oracle for the GPU** (self-consistency); (c) M5 checks end-to-end
legality via DRC pass. Because shortest-path maze routing has ties (many equal-cost
paths), "CPU == GPU" means **equal total path cost and equal per-cell congestion**, not
bit-identical routes — both implementations share one deterministic tie-break rule
(e.g. prefer lower cell index) so results are comparable.

### Milestones

- **M0 (de-risk the GPU bet, ½–1 day, CPU only — run concurrently with M1/M2; HARD GATE
  before M3):** Implement the separable H-then-V prefix-min sweep *on CPU* and prove two
  things on a battery of obstacle/clearance grids: (1) it reproduces Lee's BFS
  shortest-path distances, and (2) the shared tie-break rule (e.g. prefer lower cell
  index) is **actually reproducible under the parallel-style scan**, not just under
  serial BFS — a parallel prefix-min does not preserve a sequential tie-break for free,
  so this must be demonstrated, not assumed. If either fails under the PCB obstacle
  model, the GAMER reformulation does not transfer as-is — find the fix or re-plan M4
  before writing any Metal. This guards the single largest assumption in the design.
- **M1 (CPU correctness):** Single-layer, single-net CPU Lee/BFS router. 32x32 grid,
  one source, one target, one rectangular obstacle; routed path length equals the
  hand-computed expected length. Runnable CLI.
- **M2 (CPU end-to-end):** Parse a real board via kicad cruncher → grid → route multiple
  nets with **sequential net ordering + rip-up-on-collision only** (no cost-based
  congestion field yet). Rip-up is **bounded: max K passes (e.g. K=20); on exhaustion,
  report the list of unrouted nets and exit** — never loop unbounded. Runs on ≥1
  tscircuit dataset board; CPU baseline timing + grid size + net count recorded (the
  honesty benchmark).
- **M2 GO/NO-GO gate:** Using M2's measured grid sizes and net counts, project the
  batch-GPU speedup. If projected speedup is < ~2x, the honest move is to **pivot the
  artifact to "negative result + writeup"** ("GPU maze routing on Apple Silicon doesn't
  beat CPU at PCB scale, here's the data and why") — which is a fully valid contribution
  consistent with the learning goal. Decide here before sinking weekends into M3/M4.
- **M3 (first Metal kernel):** Metal wavefront-expansion kernel as a drop-in for ONE
  CPU step, **atomic-free** (min into a separate output buffer + ping-pong). Matches the
  CPU result (equal cost/congestion, shared tie-break) on the 32x32 case. This is the
  "I wrote my first working compute kernel" win.
- **M4 (the real GPU lesson):** Replace the naive wavefront with the **row/column
  prefix-min sweep** (validated on CPU at M0). Matches CPU result on **single-layer,
  multi-net** dataset boards (multi-layer/vias still deferred). Report speedup on the
  **batch-of-nets** workload — explicitly defined as: many nets routed concurrently
  against a **shared obstacle/congestion grid**, with collisions resolved by the same
  M2 rip-up policy (so the metric reflects real routing, not just embarrassingly-
  parallel dispatch throughput). Metric: nets/second and total wall-clock, CPU vs Metal,
  same boards.
- **M5 (whole stack closes):** Hand the global routing solution to Freerouting via
  DSN/SES for detailed routing; produce a DRC-passing board from end to end on at least
  one real design.
- **Contribution artifact:** public repo + reproducible benchmark harness on the
  tscircuit dataset + a writeup (positive OR negative result). Stretch: a PR or issue
  engaging tscircuit/Freerouting with the findings.

Explicitly NOT in early scope: multi-layer + vias (until after M4), 45°/any-angle
routing, cost-based congestion-aware global routing, ML/RL net ordering, a GUI.

## Distribution Plan

- **Deliverable:** an open-source Rust (or Swift) repo containing a CLI router + a
  reusable core crate/library + a benchmark harness.
- **How people get it:** GitHub repo (MIT or Apache-2.0); `cargo install` /
  GitHub Releases binaries for macOS arm64. Because it's Metal-only, the README states
  the platform requirement plainly and points Linux/Windows users at the algorithm +
  benchmark numbers (the portable contribution) rather than a binary.
- **CI/CD:** GitHub Actions on macOS arm64 runners — build + run the CPU test suite +
  numeric-diff routed output against checked-in reference results on a small dataset
  subset. **Open infra question:** GitHub-hosted macOS runners do not guarantee Metal
  compute access, so treat GPU benchmarking as **local-only by default**; CI stays
  CPU-correctness + reference-diff. Revisit self-hosted Metal runners only if the
  project warrants it (probably not for a learning project). Gate any GPU step so forks
  without Metal still pass.
- **Reach beyond Metal (possible future, NOT a v1 constraint):** a future `wgpu`/WebGPU
  backend could make it run cross-platform. Do **not** build a backend-abstraction layer
  up front to enable this — that's premature abstraction and fights the Metal-first,
  learn-the-hardware premise. Write the cleanest Metal code; treat a portable backend as
  a possible later rewrite informed by what you learned, not a design constraint now.

  profiling.
- **License compatibility (check before reusing):** confirm CUGR's license (used as an
  algorithm *reference*; do not copy code unless the license permits) and whether the
  tscircuit `autorouting` dataset may be redistributed (or just referenced/downloaded by
  the harness) under the new repo's chosen license (MIT or Apache-2.0). GAMER is a paper
  (ideas are free to reimplement); CUGR/dataset are code/data with terms. Resolve before
  vendoring anything.
